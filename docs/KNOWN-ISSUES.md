## Known Issues Found & Fixed

A running log of real bugs found (mostly via direct user reports against the live app, some via direct verification against real data) and how each was actually diagnosed and fixed — kept as one place to see the project's real failure modes, rather than scattered across commit messages. Newest first.

### Transfers results KeyError (2026-09-23)

- **The Transfers tab crashed with `KeyError: 'sell_price'` whenever the optimizer actually suggested a transfer** — the results dataframe's columns get renamed to display labels (`selling_price` → `"Selling price"`) just before rendering, but the bank caption underneath still read the pre-rename `out_rows['sell_price']`. The "holding is optimal" branch never touches that frame, so the crash only surfaced when transfers were genuinely returned — exactly the path no existing test drove, and only visible after clicking **Find transfers**, which is why it reached production. Fixed by reading the renamed column; `app/test_app_offline.py` now clicks that solve through Streamlit's `AppTest` on every CI run (holding path too), so the results block is rendered in tests rather than only in a browser.

### Sidebar chat assistant (2026-08-31)

Added, per explicit request ("can we add a chat bot that talks to me regarding my team and transfers ... run it with the openrouter free AI models"): a conversational chat assistant grounded in real live data.

- **Grounding scope** (explicit choice: "Broader — also let it browse Season Insights / PL Table data", not squad-only): `assemble_chat_context()` in `shared.py` assembles one compact, real-data text block on every turn from already-existing real functions — the manager's real current squad (starting XI/bench, captain/vice-captain), real injury/suspension/doubt status, real rotation-risk flags (`rotation_risk_flags()`), real banked free transfers, real chip availability this half, real top-5 league-wide differential picks (`differential_finder()`), and the real current Premier League table top 5 (`premier_league_table()`). Every fact is a real number already verified elsewhere in this app — nothing is computed fresh just for the chat.
- **Placement** (moved 2026-08-31, per explicit follow-up request "place it at bottom right or as a popup"): originally in the sidebar, now a real `st.popover()` floating chat bubble pinned to the bottom-right corner via a small CSS rule on Streamlit's own popover container — `render_chat_assistant()`, called once from `app.py`'s main body. `st.chat_input`/`st.chat_message` render inside the popover itself; conversation history lives in `st.session_state["chat_history"]` (survives reruns within a browser session, same pattern as `built_squad` elsewhere — not persisted across a real reload, which is fine for a chat aid).
- **System prompt** explicitly instructs the model to answer ONLY from the real data it's given and say so plainly rather than guess when a question needs something it doesn't have — same "never invent a stat" principle as the existing transfer-narration feature.
- **Switched from OpenRouter to local Ollama only (2026-08-31)**: the original design ran on OpenRouter's free-tier models, first a single hardcoded model, then an ordered fallback list with live availability checking — but even with fallback, free-tier models kept hitting real, frequent HTTP 429s (rate-limited) under normal interactive chat use, a genuine OpenRouter-side congestion issue outside this project's control. Per explicit request ("i do have a few ollama models locally installed can we work with that instead" → "remove open router entirely and just keep local ollama"), OpenRouter was dropped completely in favor of `src/llm/ollama_client.py`, a thin client for a LOCAL Ollama server (model: `gemma3:4b`) — zero rate limits, zero cost, no external API key, since every request is served by this machine's own hardware. `ollama_client.is_available()` is a real, live liveness check (not a config flag) used by both the chat assistant and `explain_transfer_suggestion()`.
- **Real tradeoff, accepted explicitly**: this makes both the chat assistant and "Why this transfer" narration **local-only** — they genuinely do not work when this app is deployed on Streamlit Cloud, since Ollama is never installed there. Both degrade gracefully (a plain, honest caption, e.g. "this feature only works when the app is run locally alongside Ollama" — never a crash) rather than silently failing; every other feature (live squad, transfers, chips, fixtures, PL table, etc.) is completely unaffected and keeps working normally on the live deployment.
- Verified with tests in `test_shared_live.py`: `assemble_chat_context()` genuinely contains the manager's real squad member names and the real current PL table leader; both `chat_with_assistant()` and `explain_transfer_suggestion_debug()` return a real, specific error (not a crash) when no local Ollama server is reachable (simulated via monkeypatching, not by actually stopping the real local server); a real end-to-end test confirms a genuine reply comes back from the local Ollama server when one is running.

### Real transfer-pool bugs found live (2026-08-28)

Two serious real bugs reported live and fixed:

- **The optimizer recommended transferring IN a real currently-injured player.** Reproduced exactly: it suggested replacing a real Team of the Week pick (João Pedro, real GW1 Dream Team) with William Osula — real status `'i'`, "Foot injury - Unknown return date". Root cause: `preseason_pool()`'s `predicted_points` came from last season's closing form, computed before this injury existed, and nothing ever excluded an unavailable player from being suggested as a transfer-IN TARGET — the existing injury check only ever protected CURRENT squad members from being kept for the wrong reason, never stopped an unavailable player from being recommended as the incoming pick. Confirmed directly: 118-123 of ~600 real players in the live pool are real currently-injured/suspended/doubtful at any given time, none previously excluded. **Fix:** Transfers now zeros `predicted_points` for EVERY currently-unavailable player in the whole pool (not just squad members) before the optimizer ever sees it, with a visible caption confirming how many were excluded.
- **The same real player comparison also exposed why**: `preseason_pool()`'s `predicted_points` was 100% last season's data, permanently — it never incorporated real 2026-27 performance no matter how many real gameweeks passed, so a real Dream Team performance (João Pedro) could show LOWER predicted_points than a player who'd just sat scoreless on a real bench (Pedro Porro), purely because last season said otherwise. **Fix:** added a real, weighted blend — `weight_this_season = min(current_gw / 6, 1.0)` — shifting from last season's closing form (0% weight at GW1, since a single real gameweek is genuinely noisier than a full prior season) toward this season's own real `points_per_game` (FPL's own real cumulative this-season average) as more real gameweeks accumulate, reaching 100% this-season by GW6. Verified directly: at GW1, João Pedro's predicted_points rose from 2.0 → 3.5 and Porro's fell from 4.6 → 3.83, correctly narrowing (though not yet flipping, honestly reflecting only 1/6th real weight at GW1) the wrong signal. Both bugs are now permanently guarded by a real end-to-end test (`test_transfers_never_recommends_a_currently_unavailable_player`) that reproduces app.py's exact fix against real live data.

Also added, per explicit request: **`rotation_risk_flags()`** — a real "out of favor, not injured" transfer-out signal, distinct from the existing injury/suspension check. A squad member can be perfectly fit (real `status == 'a'`, no news) while their own real manager simply isn't picking them. Bar: real 0 minutes in EACH of the last 2 real, actually-played gameweeks AND real `form` below 2.0 (both together, so a rotated-but-still-performing player isn't incorrectly flagged) — correctly does nothing before 2 real gameweeks exist this season. Uses `fpl_api.get_player_summary()` per squad player (bounded to at most 15 real calls, not the full league-wide rate-limited case), shown in Transfers with the same "treated as unavailable, predicted points zeroed" treatment as a real injury.

A real, separate need from the sidebar's squad-specific fixtures above — this shows the FULL gameweek, every match, not just the ones involving your own squad.

### Pitch/card visual pass (2026-08-27)

Asked for aesthetic recommendations; built the ones that were genuinely achievable, documented the one that wasn't rather than faking it:

- **Real pitch field markings** — the pitch view (`render_pitch()`) was a flat green gradient with no lines. Added a center circle, halfway line, and penalty-box outlines, drawn entirely with layered CSS `background-image` gradients (no extra DOM elements, keeping the single-line-HTML constraint every card here has to respect).
- **Bench box palette mismatch** — the bench strip used a flat `#222` gray, visually disconnected from the rest of the app's purple/green gradient language. Restyled to match.
- **Team-tinted missing-photo fallback** — a player with no FPL headshot showed a flat neutral gray box for every club. Added `TEAM_PRIMARY_COLOR`, a small reference table of each real 2026-27 club's actual primary shirt color — **not sourced from FPL's API** (confirmed directly: bootstrap-static has no team-color field at all), a deliberate, documented exception to this project's usual live-API-first rule, since these are genuine public facts about a club's identity, not something that changes or needs live verification. Uses `color-mix()` at a light 12% blend so the real team badge drawn on top stays legible; a plain-gray fallback declaration is layered underneath for a browser too old to understand `color-mix()`.
- **Dataframe header-row tinting was investigated and confirmed NOT achievable**: `st.dataframe` renders via `glide-data-grid`, a canvas-drawn grid, not real DOM `<thead>` elements — there's no CSS selector or Streamlit `column_config`/`Styler` API that reaches inside a canvas element's header row. Documented directly in `inject_shared_css()` so this isn't silently reattempted later; the container-level rounding/border already applied is the real achievable ceiling without replacing every table with custom HTML (a much larger rewrite trading away real sorting/scroll performance for a header-color tint).

### Chip tracking correctness + visual pass (2026-08-27)

- **`chip_usage_status()` incorrectly treated a chip as used for the whole season, not per half.** FPL's own real rule (verified directly against bootstrap-static's `chips` array): EVERY chip, not just Wildcard, is available once per half of the season, each half with its own real `start_event`/`stop_event` window. The original version would have shown a chip as permanently "used" after its first-half play even once a fresh copy became available in the second half. **Fix:** now derives the real current half's window from bootstrap and only counts a play as "used" if its gameweek falls inside that specific half's real window.
- **A real, valid third state was missing**: at GW1, Wildcard/Free Hit's real first-half window hasn't opened yet (starts GW2) — confirmed live, not assumed. The chip panel now distinguishes "Available," "Used," and "Not open yet" instead of only two states, and the panel itself was restyled as icon cards (🃏🎯🪑👑) instead of plain metric boxes, with used/not-yet-open chips visually dimmed.
- **Security fix**: the new gradient-card styling for "Why this transfer" required `unsafe_allow_html=True`, which the plain version never used — the real LLM output is now passed through `html.escape()` before being embedded, since unescaped external text inside a raw-HTML block is a real injection risk regardless of how grounded the model's facts are.

### AI transfer narration (2026-08-27)

The Transfers tab now shows that real reason as a caption instead of staying blank.

- **A real HTTP 429 (free-tier rate limit) showed the same alarming error caption as a genuine failure.** A 429 is an expected, normal condition for a free model under load, not a real problem worth surfacing on every click. **Fix:** tagged real 429 responses with a `RATE_LIMIT_PREFIX` marker in `openrouter.py`, and the Transfers tab now stays silent specifically on that case while still surfacing every other real error. Verified with a monkeypatched HTTPError(429) rather than trying to force a live rate limit on demand.

### Full-codebase audit (2026-08-27)

Requested an end-to-end sweep of the collector, model, and dashboard layers for real gaps beyond what direct user reports had already surfaced. Ranked findings acted on:

- **Season string hardcoded to "2026-27" in 8 places** (`app/shared.py`'s fallback paths, plus `app/app.py`'s `_collected_gws()`), correct today but silently wrong (pointing at a folder that no longer exists) the day the season rolls over to 2027-28. Fixed by adding `_current_season_label()` (same derivation `snapshot.py`'s own `_season_label()` uses — the real bootstrap's first gameweek deadline) and routing every call site through it, instead of a repeated literal. `src/collector/refresh_dashboard_fallbacks.py` had the same bug in 3 places, fixed the same way (`_current_season_dir()`, globbing `data/raw/*` like `refresh_bootstrap()` already correctly did, instead of hardcoding it). A permanent regression test (`test_no_hardcoded_season_path_in_shared` in `app/test_shared_live.py`) now scans both files' actual source for the literal path-segment pattern.
- **Chip Advisor was missing Free Hit and Wildcard entirely** despite `chips.py` supporting both — the tab only ever covered Bench Boost and Triple Captain. Added a real single-gameweek Free Hit/Wildcard check using a new `ep_next_player_pool()` (every available player, real `ep_next` as `predicted_points`, matching the SAME real field the rest of this tab already uses — deliberately not `preseason_pool()`'s different, last-season-form field, which would silently compare two different numbers as if they were the same).
- **`optimize_transfers`'s `unlimited_transfers=True` path (the real code path Wildcard/Free Hit/GW1 squad-building takes) had zero test coverage.** Added two new tests to `src/model/test_optimizer.py`: one exercising the unlimited path end-to-end against real data (verified it never reports a paid transfer/hit cost, and scores at least as well as the gated path from the same starting point, since it has strictly more freedom), and one confirming the real `ValueError` guard fires cleanly when a squad member is missing from the pool (e.g. already sold) instead of a confusing raw `KeyError` from inside the solver.
- **Two Transfers/Chip Advisor captions implied a future automatic improvement that isn't actually wired up** ("a real current-season model will automatically start being used here once enough live gameweeks are collected") — no code path actually swaps the pre-season pool for a live-gameweek model-based one; that needs real data-pipeline work (wiring live 2026-27 gameweeks into the trained model's feature pipeline) that hasn't been built. Corrected the caption to say this is a standing limitation needing that pipeline work, not something that resolves itself with time.
- Minor robustness fixes: `build_live_squad_df()` now guards against a `None` `picks_data` (documented as a real possible return from its loader, previously unguarded) rather than raising a raw error; `differential_finder()`/`league_wide_status_flags()`/`season_leaderboards()` now guard `selected_by_percent` casts with `or 0` for consistency with the rest of the file's defensive-casting pattern, matching a real edge case (a brand-new player with no ownership data yet) even though not currently observed live.

### Live-sync (2026-08-24)

- **Season Insights/PL Table/etc. showing stale data despite "live" loaders** — the deepest of three stacked bugs found in the same investigation:
  1. *No live API call at all.* Every Home-page number originally read only from `data/raw/` (local, manually refreshed) or a once-a-day GitHub Actions batch commit — there was no direct FPL API call anywhere. **Fix:** added live-first loaders (`_load_bootstrap()`, `_load_fixtures_df()`, `_load_entry_history()`, and the picks/live-points/league-standings loaders) that call the real FPL API directly with a 60s `st.cache_data` ttl, falling back to files only if the live call itself fails.
  2. *A fresh cache value doesn't trigger a rerun.* Even with live loaders in place, tabs were plain `with tab_x:` blocks — Streamlit only re-renders when something triggers a rerun, so a 60s-fresh value sitting behind an untouched tab never reached the browser. **Fix:** wrapped every Home tab in `st.fragment(run_every=60 if is_gameweek_live() else None)`, gated on a real "is a gameweek actually in progress" check so nothing polls 24/7 for no reason.
  3. *The real root cause, found last:* eight functions built on top of the (correctly 60s-ttl'd) loaders — `live_price_changes()`, `likely_price_movers()`, `differential_finder()`, `league_wide_status_flags()`, `premier_league_table()`, `team_insights()`, `season_leaderboards()`, `team_upcoming_fixtures()` — were themselves decorated with a bare `@st.cache_data`, no ttl of their own. Bugs 1 and 2 were both genuinely fixed, but didn't matter: Streamlit had already cached these functions' own return values forever. Confirmed directly — a real player's (Cherki) real 2nd assist never appeared on the Assists board until `ttl=60` was added to all eight. A permanent regression test (`test_every_live_facing_function_has_a_cache_ttl` in `app/test_shared_live.py`) now reads `shared.py`'s own source and fails if any live-facing function loses its ttl again.
- **GW points metric showed 15 while the real per-player feed already summed to 18** — FPL's own `entry_history["points"]` summary field lagged its OWN `event/{gw}/live` per-player numbers for a short window mid-gameweek. **Fix:** the headline metric and the "2026-27 progress" chart's latest row are now both summed directly from the same real per-player points already rendered on the pitch, not trusted from the summary field.
- **"No game time" conflated two different real states** — a player whose team hadn't played yet this gameweek looked identical to one whose match was over and who simply wasn't used. **Fix:** added `_team_fixture_started()` (real fixtures.csv `started` field) so the two now show distinct, accurate labels: "Not yet played" vs. "No game time."
- **PL Table/fixture-difficulty features had no data at all on a fresh deploy** — `data/raw/2026-27/fixtures.csv` lives under the gitignored `data/raw/` tree, so the deployed app never had this file, in any state, regardless of how much real gameweek data existed. **Fix:** added a committed `data/dashboard_fixtures.csv` fallback (same pattern as the bootstrap fallback below) and wired it into the daily refresh workflow, which had also been missing this specific file from its commit step.

### Collector / data pipeline

- **`element` (player id) silently blends unrelated players across seasons** — FPL reassigns this id every season (id 1 is a different real player in every one of 9 loaded seasons); any rolling/lagged feature grouped by it would corrupt silently. **Fix:** joined in `player_code`, FPL's actual stable cross-season id, verified against Salah's real code staying constant across 8 seasons while his `element` id changed every year.
- **`opponent_team`/`team` are also season-scoped numeric ids, same bug class** — id 4 is Chelsea in 2016-17, Burnley in 2020-21, Brentford in 2022-23; using it raw would silently corrupt any opponent-strength feature. **Fix:** resolved to real team name strings via `teams.csv` per season, with a `master_team_list.csv` fallback for the three earliest seasons that lack one.
- **Player names corrupted for 2019-20 onward (`Ekitike` → `EkitikÃ©`)** — the vaastav dataset's encoding isn't consistent across seasons (2016-17 to 2018-19 are genuinely Latin-1; 2019-20 onward are genuine UTF-8), but the loader read every season as Latin-1 unconditionally. **Fix:** encoding is now resolved per season instead of assumed globally; verified at the raw byte level, not just terminal display.
- **A manager's own live picks/points were invisible for days after being genuinely available** — the collector gated a manager's own picks fetch on the same `data_checked` flag used for the expensive league-wide stats fetch, which only flips a day or two after a gameweek fully finishes. Confirmed directly: GW1 returned real picks/points via the live API while `data_checked` was still `false`. **Fix:** decoupled entry snapshotting onto its own, looser check (`finished OR is_current`).

### Dashboard

- **Deployed app crashed entirely on pre-season/manual squad modes** — `data/raw/` is gitignored, so a fresh Streamlit Cloud deploy had zero bootstrap data to load, and both the optimizer and the dashboard crashed outright. **Fix:** added `data/dashboard_bootstrap.json`, a deliberately-committed non-timestamped fallback; verified by moving `data/raw/` aside entirely to simulate a real fresh deploy and confirming the same squad still built correctly from the fallback alone. The same class of gap later hit Manager History (`data/dashboard_entry_history.json`) and PL Table (`data/dashboard_fixtures.csv`) — same root cause, same fallback pattern, found and fixed separately each time as new features started depending on previously-untouched gitignored files.
- **Pitch view showed literal `<div>` text instead of rendering** — `st.markdown(unsafe_allow_html=True)` runs Markdown parsing before HTML rendering, and Markdown treats 4+ leading spaces as a literal code block; the HTML-building f-strings were indented for Python readability, which broke exactly the nested (more-indented) rows. **Fix:** rebuilt as single-line, zero-indentation string concatenation, with a docstring warning against reintroducing indentation.
- **Broken player photos showed the browser's ugly broken-image icon** — a JS `onerror` handler doesn't fire reliably through Streamlit's sanitized HTML rendering, so a real 403 from FPL's photo CDN (missing photos are genuinely absent, not a placeholder) left a visibly broken image instead of a clean fallback. **Fix:** CSS-only approach — a wrapping div carries the player's real team badge as a `background-image`, which shows through automatically when the `<img>` fails, no JS needed.
- **Player photos showed heads cropped off** — the image box used `object-fit: cover` at a fixed height that didn't match FPL's real photo aspect ratio (genuinely 220×280, checked directly from the file header, not the misleading "110x140" the URL implies). **Fix:** switched to `object-fit: contain` at a box height matched to the real ratio.
- **Switching Squad Builder modes showed a stale squad from the previous mode** — `st.session_state["built_squad"]` persists across reruns by design, so switching modes kept showing the old squad under a freshly-selected new one. **Fix:** cleared the relevant session-state keys whenever the mode selection itself changes.
- **Transfers dead-ended for pre-season/manual squads** — those squads set a session sentinel Transfers read as "no next gameweek exists," even though the transfer optimizer doesn't actually need one, just a player pool. **Fix:** Transfers now re-fetches the live pool directly for these squad types instead of refusing to run.
- **A materially noisy player pool triggered 4 hits (-12pts) for one real squad** — the marginal-gain gate for suggesting a paid transfer was working correctly, but its safety margin (tuned for the trained model's real predictions) was too permissive for the much noisier last-season-form pool used pre-season. **Fix:** doubled the margin specifically for that pool; verified it now correctly settles to 1 sensible free transfer while a real injury (simulated by zeroing a starter's points) still clears the stricter bar and takes the hit.
- **Free transfers were a manual slider defaulting to 1, never reflecting reality** — **Fix:** added `calculate_free_transfers()`, which simulates the manager's real banked transfers from their actual `event_transfers` history using FPL's real banking rule (verified against `game_settings.max_extra_free_transfers`), correctly excluding GW1's squad build (not a real "transfer" in FPL's own accounting).
